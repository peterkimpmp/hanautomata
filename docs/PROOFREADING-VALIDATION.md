# 교정 개발판은 빌드됐으며 정확도·지연·앱 인수는 승격 조건으로 남는다

- 분리 검사기와 Windows·macOS 개발 빌드를 검증했다.
- 79개 자체 예문의 규칙 포함 top-3는 68.97%다.
- 오류 집중 300자 p95 약 1.12초로 목표 300ms를 넘었다.
- 독립 검수 1,000문장과 전체 실앱 인수는 미완료다.

**판정:** M0~M4의 실험 구현·빌드·비교를 진행했다. 일반 사용자 기능으로 승격할 조건은 아직 충족하지 못했다. 기준은 `d6ad4ae` / 0.5.0이며 새 코드는 같은 버전의 개발 증분이다. [사용법](PROOFREADING.md), [단계별 판정](PROOFREADING-ROADMAP.md).

```mermaid
flowchart LR
  S[공개 사전·분리 프로세스] --> T[계약·취소·실사전 회귀]
  T --> B[Windows·macOS 개발 빌드]
  B --> Q[정확도·오류문 지연 목표 미달]
  Q --> U[독립 검수·실제 앱 인수 후 승격 판단]
```

## M2~M4 구현과 현재 검증

검사기는 `--serve` 감독기와 별도 네이티브 자식으로 분리했다. 새 요청이 이전 요청을 대체하고, 취소·EOF·3초 기한에 자식을 종료·회수한다. 검사 UI는 원문·문서·요청·리비전·UTF-8/16 범위를 다시 확인한 뒤 사용자가 선택한 한 제안만 적용한다. Windows 트레이는 UIA의 원자적 교체 한계를 피하기 위해 명시적 복사만 제공한다. TSF는 owner apartment의 edit session, macOS는 IMK 클라이언트와 포커스 epoch를 사용한다.

| 검증 | 현재 관측 | 경계 |
|---|---|---|
| macOS 검사 crate | 기본 22 + 실사전 1 + 실제 worker 2 통과 | CLI·규칙·취소·대체·기한·과대 프레임·회복; GUI 인수와 다름 |
| Python | 준비/고지 회귀 3 통과 | 손상 자료·고지 누락 거부 |
| Clippy | 모든 target 경고 0 | macOS 호스트에서 실행 |
| Swift | 원문 계약 12, key map 71, 입력 로직 166 통과 | 입력 로직 10,000키 p99 약 0.019ms; 실제 앱 입력 지연은 아님 |
| .NET | 교정 계약 11 통과, 전체 net48·helper·Preview 컴파일 | macOS의 .NET 9.0.319로 검사; GUI 실행은 아님 |
| TSF target 검사 | x64 Windows GNU cargo check 통과 | 실제 Windows 검증은 아래 기록 |
| Windows 365 | 검사기·공유 core·TSF·WinForms 빌드/테스트 실행 | 초기 빌드 시점에는 IME 미등록; 후속 설치는 아래 별도 기록 |
| 원격 CI | Linux/macOS/Windows 작업 정의 추가 | 실행 결과를 확인하지 않음 |

macOS에서 일시정지 상태가 검사 허용 조건에 빠진 것을 새 테스트의 실패로 확인하고 보완했다. Swift의 정규형 동등 비교가 다른 원문 바이트를 동일하게 취급하는 실패도 재현했다. 현재 원문·선택 스냅샷은 UTF-8 바이트를 비교하며, 보호어만 정규형 동등 비교를 사용한다. 기존 core 테스트 한 번은 `open_seeded`의 `Busy`로 실패했다. 해당 1개를 정확한 이름으로 재실행한 뒤 전체 기본 회귀와 macOS 빌드를 다시 통과했으며, 기존 core 소스를 변경하지 않았다.

macOS 독립 편집기를 실제로 실행하고 선택문과 검사기 자식 실행을 확인했다. 사용한 CUA는 key window만 반환하여 별도 nonactivating 패널을 직접 관찰·조작하지 못했고, aside의 로컬 UI 도구는 브라우저 전용이었다. 따라서 macOS 패널의 실제 클릭 적용·Undo·IMK 앱 인수를 통과로 표시하지 않는다. 이 도구 제한을 제품 결함 또는 제품 성공으로 해석하지 않는다.

### Windows 365 네이티브 빌드

사용자가 지정한 Windows 365에 aside 원격 호스트로 접속했다. Windows 11 Enterprise build 26300, PowerShell 7.6.4, Python 3.12.10, Rust 1.99.0 Windows GNU, LLVM-mingw 20261006 UCRT/Clang 23.1.3, libclang 18.1.1을 사용했다. 도구는 프로젝트 전용 폴더에 준비하고 빌드 프로세스의 환경 변수만 설정했다. 이 초기 빌드 단계에서는 전역 PATH와 설치된 IME를 변경하지 않았다. 이후 사용자 요청으로 수행한 설치·업데이트와 설치 경로에서 발견한 회귀는 [별도 설치 기록](PROOFREADING-INSTALLATION.md)에 구분한다.

| 실제 Windows 실행 | 결과 |
|---|---|
| 검사기 기본 회귀 | 21개 통과; Unix 전용 옵션 인코딩 검사는 해당 없음 |
| 실사전 및 native worker | 1 + 2개 통과; 취소·대체·시간 초과 후 회복 포함 |
| 공유 core | 132개 통과, 기존 수동 항목 2개 ignored |
| TSF x64 | 단위 191 + 통합 12 + shell 19 = 222개 통과, 기존 항목 7개 ignored |
| TSF x64·x86 | release DLL/설정 도구 빌드 및 무등록 selftest 통과 |
| .NET Framework | 원문 계약 11개 통과, 트레이 본체·helper·독립 Preview 컴파일 |

x86 교차 링크의 `gcc`/`gcc_eh` 탐색 실패는 i686 호스트 도구로 빌드하여 해결했다. x64의 CRT 검색 순서도 해당 빌드 환경에서 조정했다. 이 환경의 성공을 MSVC·ARM64·모든 Windows 툴체인 성공으로 확대하지 않는다. 패키징의 C# 상대경로 오류는 실제 실패 로그로 재현한 뒤 절대경로 인자로 수정했다. DLL selftest는 COM 활성화·호스트 문서 교체·실행취소 인수를 대체하지 않는다.

수정된 `build-windows.ps1`을 직접 실행한 재빌드는 **exit 0**이다. `C:\dev\hanautomata-proofreading-20261016\build\script-verified-windows`의 48개 파일과 하위 검사 payload의 45개 파일을 각각 전체 목록·크기·SHA-256으로 확인했다. Rust 런타임 크레이트 원본 22개, 사전 대응 소스, `libc++.dll`·`libunwind.dll`, 공식 런타임 고지 8개를 보존했다. 추가 DLL의 출처와 라이선스는 Cargo 고지와 별도이며, 원본 LLVM-mingw 아카이브와 고정 LLVM 커밋을 기록했다. 원래 전체 빌드와 evidence는 덮어쓰지 않았다.

[Windows 실행·해시 기록](../core/tools/proofread/observations/20261016-windows-verification.json)에 검사 수, x64/x86 바이너리 해시와 패키지 해시가 있다. 원격 `evidence/final-results.json`의 스크립트 blocker는 **수정 전 이력**이며 `evidence/script-fix-result.json`이 해제 근거다. 로컬 사본과 실제 process-only 빌드 환경은 `build/evidence/`에 보존했다.

Windows 365의 기존 aside 탭에서 독립 편집기의 합성 원문·선택 상태와 제안 패널을 직접 관찰했다. 패널에는 원문·선택 영역·입력 칸 변경 거부 문구가 표시됐다. 시험 도중 활성 앱과 창 위치가 바뀌어 통제된 조건의 제안 적용·Undo·보호어·취소/재검사를 끝내지 못했다. **이 초기 거부를 제품 결함이나 안전성 통과로 확정하지 않는다.** 다른 화면 작업과 충돌하지 않는 재시험이 필요하며, 독립 편집기의 실행도 설치된 TSF의 실제 앱 인수를 대신하지 않는다.

### 동일 평가셋의 엔진 비교

`evaluation/cases.json`은 직접 작성한 **정상 45 + 오류 29 + 보호어 5 = 79건**이다. 원천 N=79, 출력 N=79(엔진별)이다. 독립 언어 전문가의 검수나 무작위 실사용 표본은 아니다. 규칙 작성에 사용한 오류 5건은 `rule-development`로 표시하여 제외한 집계도 함께 낸다. 사전 단독·정확 어절 규칙·Kiwi 원시 띄어쓰기를 같은 문장에 실행했다.

| 지표 | Hunspell | Hunspell + 5어절 규칙 | Kiwi space 기준선 |
|---|---:|---:|---:|
| 문장 탐지 precision | 100% | 100% | 63.16% |
| 오류문 탐지 recall(29건) | 82.76% | 86.21% | 41.38% |
| 정확 전체문장 top-1 | 44.83% | 62.07% | 34.48% |
| 정확 전체문장 top-3 | 51.72% | 68.97% | 34.48% |
| 규칙 개발 5건 제외 오류 24건 top-3 | 62.50% | 62.50% | 25.00% |
| 정상 45건 오탐 | 0/45 | 0/45 | 7/45 |
| 보호어 5건 불변 | 5/5 | 5/5 | 5/5(전체 요청 보류) |

precision/recall은 **오류가 있는 문장에 무엇이든 표시했는지**를 보는 분류 값이다. 오류 위치를 정확히 찾았다는 점수는 아니다. top-k는 하나의 진단에서 후보 순위 k 이하의 단일 치환 결과가 허용된 전체 정답문과 일치해야 한다. 전역 문장 후보 순위나 문맥 교정 전체 정확도로 부르지 않는다. 전체 top-3 개선은 규칙 개발 예문에서 발생했으며, 제외 집계의 62.5%는 개선되지 않았다. 정상문 0/45 역시 목표인 독립 검수 1,000문장 오탐률을 입증하지 않는다.

Kiwi 0.24.0은 `Kiwi(num_workers=1, typos='basic').space(reset_whitespace=False)`로 실행했다. kiwipiepy_model 0.24.0, numpy 2.0.2, tqdm 4.70.1, Python 3.9의 별도 venv다. 코드·URL에 대해 같은 보호 어댑터를 구현한 제품 후보가 아니며 보호어가 있는 요청 전체를 보류한다. **이 원시 기준선 결과는 Kiwi 전체 성능 순위가 아니다.** 현재 비교로는 기본 제품에 도입하지 않는다.

재현 명령과 엔진별 전체 결과:

```sh
python3 core/tools/proofread/evaluate.py \
  --binary core/tools/proofread/target/release/hanautomata-proofread \
  --dictionary build/proofreading-data --output build/native-evaluation.json
# 별도 venv에 위 버전들을 설치한 뒤:
python core/tools/proofread/evaluate.py --kiwi-only --output build/kiwi-evaluation.json
```

[사전·규칙 원시 결과](../core/tools/proofread/observations/20261016-native-comparison.json), [Kiwi 원시 결과](../core/tools/proofread/observations/20261016-kiwi-comparison.json). 두 결과의 corpus SHA-256은 `0e0539306ce56d0da6abf0f95407cc27fe0262bc8d81208f50169b9b198a0197`로 같다.

### 300자 지연과 메모리

Apple M5 / macOS 26.6.2 / arm64 release에서 정상문과 오류문을 별도로 결합한 300자 입력을 각각 30회 검사했다. native 시간에는 JSONL IPC 왕복이 포함된다. Kiwi는 같은 Python 프로세스의 함수 호출이다. 파일 캐시를 비우지 않았고, 머신이 유휴라고 가정하지 않는다. 300자라는 길이가 실제 오류 분포를 대표하지는 않는다.

| 관측 | Hunspell | 규칙 포함 | Kiwi space |
|---|---:|---:|---:|
| 첫 요청/초기화 1회 | 185.1ms | 190.1ms | 849.3ms |
| 정상 300자 warm p95 | 6.35ms | 6.37ms | 1.49ms |
| 오류 집중 300자 warm p95 | 1,171.45ms | 1,117.66ms | 1.78ms |
| 관측 메모리 | 63.72MiB | 63.67MiB | 577.73MiB |

native 메모리는 **5ms RSS 표본의 최댓값**, Kiwi는 Python과 모델을 포함한 **OS 프로세스 high-water mark**다. 측정 방식이 달라 정확한 배수 비교에는 사용하지 않는다. 메모리 수치는 UI·감독기까지 합산한 전체 제품 수치도 아니다. 빠른 정상문 결과로 오류문 지연을 감추지 않는다. 현 구성은 오류 밀도가 높은 문장의 300ms 목표에 미달하지만 입력기 키 처리 스레드는 기다리지 않는다.

### 승격 게이트와 배포 경계

| 조건 | 판정 |
|---|---|
| 독립 검수 정상 1,000건, 오탐 ≤1% | 미확보 |
| 고정 오류셋 top-3 ≥80% | 현재 개발 예문에서도 미달 |
| 300자 warm p95 ≤300ms | 오류 집중 입력 미달 |
| 실제 앱의 안전한 단일 적용·Undo·포커스·보안·조합 보호 | 전체 인수 미완료 |
| 플랫폼별 자체 빌드·고지·사전 대응 소스 | 개발 payload 검증; 공개 패키지 인수와 구분 |
| 개발판 설치·업데이트 | [실호스트 설치 기록](PROOFREADING-INSTALLATION.md)의 플랫폼별 판정 적용 |
| 배포용 서명·공증·공개 릴리스 | 미수행; macOS 개발 빌드의 ad-hoc 서명과 구분 |

macOS payload에는 본체 LICENSE, 해당 target의 Rust 의존성 원본·고지, 한국어 사전 원고지·전체 대응 소스, 파일 해시 MANIFEST를 보존했고 앱과 데모의 ad-hoc 서명을 검증했다. Windows의 추가 C++ 런타임은 Cargo 고지와 별도로 보존·검증했다. 이 인벤토리는 공개 배포의 모든 법적·보안 인수를 완료했다는 뜻은 아니다. 국립국어원 신청형 말뭉치, 사용자 입력 로그, Kiwi 모델은 제품 payload에 포함하지 않는다.

## 초기 M0~M1 측정 기록

아래는 같은 날 첫 CLI 증분에서 보존한 기록이다. 현재 구현·검증 범위는 위 M2~M4 절과 플랫폼 실행 기록을 따른다.

### 엔진 선택의 실행 근거

동일한 한국어 `ko.aff`·`ko.dic` 0.7.94로 두 엔진을 직접 실행했다. Spellbook 0.4.2는 `안녕하세요`, `돼요`, `됐다`, `학교에`, `먹었습니다`를 모두 거부했다. 따라서 pure Rust 구현이라는 장점만으로 채택하지 않았다. 원인에 대한 라이브러리 내부 분석·수정은 이번 범위에 포함하지 않는다.

Hunspell 1.7.1은 같은 5개 정상 활용형을 모두 허용했다. 다음은 현재 CLI 경로에서 관측한 NFC 결과다. 문맥 없는 개별 어절이며 사전의 품질 한계를 숨기지 않는다.

| 입력 | 진단 | 앞 후보 또는 한계 |
|---|---|---|
| 안녕하세요 · 돼요 · 됐다 · 학교에 · 먹었습니다 | 없음 | 정상 예문 5개 |
| 됬다 | `unknown_word` | 됐다 · 되다 · 뎄다 |
| 웬지 | `unknown_word` | 왠지 · 웨지 · 웨진 |
| 개발됬다 | `unknown_word` | 개발됐다 · 계발됐다 · 개발되다 |
| 되요 | 없음 | 놓친 오류. 규범성 검사가 더 필요함 |
| 할수있다 | `unknown_word` | `밀수입하다`; 기대한 띄어쓰기 후보 없음 |

단순 사전 검사에서 통과한 말도 표준 표기라고 보장하지 않는다. 특히 `되요`와 띄어쓰기는 후속 규칙·형태 분석 비교에서 다뤄야 한다. 원어민 글쓰기 전체의 precision/recall, Kiwi 대비 정확도는 측정하지 않았다.

### 초기 자동 검증

| 검증 | 관측 결과 | 범위 |
|---|---|---|
| Rust 계약 테스트 | 10개 통과 | 정상·보호어·범위·NFD·이모지·상한·오래된 결과·요청 범위 캐시 |
| CLI 테스트 | 5개 통과 | JSON·UTF-8·입력 크기·사전 실패·도움말·잘못된 옵션 인코딩 |
| 사전 실패 처리 | 2개 통과 | 누락·변조 시 엔진 진입 전 거부 |
| 고정 실사전 검사 | 별도 1개 통과 | 정상 5개+오류 3개 × NFC/NFD = 16회 검사 |
| Python 준비·고지 회귀 | 3개 통과 | 손상 아카이브 보존·누락·마지막 의존성 고지 누락 회귀 |
| Clippy | 경고 0 | 새 crate의 모든 target |
| 기존 Rust 코어 | 전체 기본 release 테스트 통과 | 기존에 ignored인 보조·수동 항목은 별도 실행하지 않음 |
| 버전 검사 | 4개 Cargo.toml 포함 통과 | 제품 버전 0.5.0 유지 |

계약 테스트는 구현 전 실패를 확인했고, 반복 어절 캐시 테스트도 중복 엔진 호출 실패를 재현한 뒤 통과시켰다. 사전 누락을 ‘정상 문장’으로 반환하지 않는지, 실패 로그가 입력을 되풀이하지 않는지 별도로 확인했다. 이 첫 증분 당시에는 .NET SDK와 Windows 검증이 없었고, 후속 검증은 상단에 기록했다. 원격 CI 실행은 계속 미확인이다.

### 초기 반복문 실행 성능

환경은 Apple M5, macOS 26.6.2, `aarch64-apple-darwin`, Rust 1.96.0이다. 릴리스 빌드에서 합성 280자 문장(6어절 패턴 10회, 총 60어절)을 한 엔진 인스턴스로 30회 검사했다. 각 요청은 오류 후보 30개를 만들며 작업 제한에 도달하지 않았다. p95는 정렬된 30회 중 29번째 값이다. 각 호출 사이에 문장 캐시는 유지하지 않았다.

| 관측 | 요청 내부 캐시 전 | 캐시 후 |
|---|---:|---:|
| warm p50 | 534.3 ms | 53.3 ms |
| warm p95 | 538.3 ms | 53.5 ms |
| warm 최댓값 | 539.0 ms | 53.7 ms |
| 해시 검증+사전 로딩, 1회 | 183.6 ms | 182.8 ms |

반복 어절에 유리한 합성 입력이므로 약 10배 개선을 일반 문장에 적용하면 안 된다. cold 값은 단 한 번의 초기화이며 운영체제 파일 캐시를 비운 cold-start 실험이 아니다. UI 목표 300자 warm p95 300ms의 통과 판정에는 다양한 독립 문장과 대상 기기의 추가 측정이 필요하다. 이번 결과는 기존 키 입력의 지연을 측정한 것도 아니다.

새 CLI 릴리스 파일은 이 호스트에서 **1,264,560바이트**다. 한국어 사전 2개는 총 **13,958,942바이트**이며 별도로 로딩한다. 메모리 최고 사용량·Windows/Intel 성능은 미측정이다. 사전 데이터를 매 키마다 읽거나 엔진을 매번 생성하는 UI 연결은 권장하지 않는다.

원시 관측은 [합성 실행 기록](../core/tools/proofread/observations/20261016-macos.json)에 보존한다. 실행 시간은 환경에 따라 달라지므로 CI의 절대 시간 단언으로 사용하지 않는다.

첫 증분 이후 프로세스 제한·UI·호스트 교체 어댑터·비교 평가를 구현했다. 현재 남은 조건은 상단의 승격 게이트 표를 따른다. 상시 문장 수집·입력문 서버 전송·자동 교정은 구현하지 않는다.
