## 실제 앱 합성 키 시험 (2026-10-12)

실물 키보드가 아니라 화면 조작 도구가 보낸 키 이벤트로 시험했다. 키는 실제 앱과 InputMethodKit 경로를 그대로 지나가지만(진단의 이벤트 출처 `state 0`), 사람의 타이핑 속도·리듬과 오른쪽 ⌘ 같은 장치 구분 비트는 재현하지 못한다. 그래서 G2 통과로 세지 않는다.

- 대상: TextEdit·Microsoft Word·메모. 브라우저는 읽기 전용이고 터미널·VS Code는 클릭만 되는 권한 등급이라 시험하지 못했다. 카카오톡·Slack·Notion은 발송·동기화 위험 때문에 빼고, 사람 확인으로 남긴다.
- 후보창(F)은 화면 캡처에 나오지 않아 확인하지 못했다. 전환 키(G)는 이 Mac의 macOS 설정이 ⇧Space와 Caps Lock을 먼저 가져가서 '설정 충돌'이다.
- 진단(입력기 몫 = 앱 응답 대기 제외): Word 67키에서 전체 p50 ≤ 5ms·p99 ≤ 62.9ms였다. 입력기 몫은 p50 ≤ 0.2ms·최대 5.18ms였다. TextEdit는 전체 대부분이 1~2ms였다.

찾아서 고친 것(자세한 내용은 CHANGELOG):

1. 원격 데스크톱 프로필의 영문 시작이 다른 앱으로 번졌다.
2. vi 모드 Esc의 영문도 같은 방식으로 번졌다.
3. 재설치하면 시스템 설정 창이 앞으로 나왔다.
4. 옛 zip을 `unzip`으로 풀면 서명이 깨졌다.
5. 재설치 뒤 입력기가 다시 뜨지 않았다.

고치지 않은 관찰:

- Word: ←로 확정하면 글자는 들어가지만 커서가 움직이지 않는다. TextEdit·메모에서는 움직인다[I: Word 동작].
- Word: Shift+F2가 입력기에 오지 않는다. 진단에 뒤집기 시도 0으로 남았고, Word 단축키가 먼저 가져가는 것으로 보인다[I].
- TextEdit: ⌥F2 뒤 ⌘Z를 누르면 뒤집기만이 아니라 앞서 친 글자까지 한꺼번에 되돌아간다. 앱의 입력 되돌리기 묶음에 합쳐지기 때문이다[I].
- 입력기 프로세스를 여러 번 다시 띄우는 동안 계속 열려 있던 TextEdit는 입력 소스를 바꿨다 되돌려도 다시 연결되지 않았다(앱을 다시 열어야 함). 개발 중 재설치에서만 생기는 일로 본다[I].
- Default Folder X(저장 창 확장)가 저장 창의 Esc를 받아 창을 펼쳤다. 입력기는 Esc를 그대로 넘겼다.

## 준비

- `./build.sh --test && ./install.sh` → 입력 소스에 한오토마타를 추가한다. 고정 모드 아이콘까지 보려면 두 고정 모드도 추가한다.
- `Hanautomata --check`로 ⇧Space·Caps Lock과 겹치는 시스템 설정을 확인한다. 겹치면 그 전환 키 항목은 '설정 충돌'로 적는다.
- 시작 전에 `Hanautomata --diagnose reset`을 실행한다. 끝난 뒤 `--diagnose` 출력을 기록에 붙인다. 출력에는 통과 사유·확정 경로·지연·이벤트 출처가 들어 있다.
